# Account security and verification

This assessment covers the schema 9 account system, including the browser and API session lifecycle, local passwords, Steam sign-in, passkeys, TOTP, account recovery, and administrator access. It also covers the points where that lifecycle meets guest capabilities, demo ownership, and async provider requests. The deployment model is a single Fastify web service with SQLite behind the operator’s HTTPS proxy. [Architecture](ARCHITECTURE.md) · [Instance setup](ACCESS-SETUP.md) · [Security model](../SECURITY.md)

The tables identify source controls, regression tests and remaining gaps for this subsystem. The verification record distinguishes executed checks from source inspection. The scope is narrower than a whole-application ASVS assessment. Hardware attestation, physical-device behavior and deployed reverse-proxy assurance require separate evidence. ## Threat model

**Assets.** Protect account credentials, password and session verifiers, TOTP seeds and the instance encryption key, individual recovery codes, the recovery exchange, and the association between passkey public keys and member identities. Protect member and administrator privileges, audit records, private demos and notes, provider secrets, and operator control over account lifecycle. Availability includes keeping a usable administrator and preserving the ability to sign in under abuse or partial failure.

**Trust boundaries.** Treat browsers, uploaded data, displayed provider data, IP forwarding headers, and every submitted identifier as untrusted. The app makes authorization decisions from server-side state. The operator’s proxy is trusted for TLS and source addressing only when its socket address is explicitly trusted and the forwarding chain yields an unambiguous client address. The app trusts Steam to validate its own signed OpenID assertions and uses only the immutable Steam subject for identity. A FACEIT profile is match-source data. The deployment operator controls the server and has privileged access to local CLI commands, database files, backups and the encryption key. Host or proxy compromise can defeat the application controls. [Provider configuration](ACCESS-SETUP.md#steam-and-faceit) · [Deployment model](ARCHITECTURE.md#deployment-and-data-flow)

A separate, server-issued HttpOnly browser cookie orders account grants across tabs. SQLite stores its digest alongside each session. A stolen binding can allow sign-out of sessions in that browser’s revocation scope. Independent browsers and private account data require their own credentials. Presenting this cookie alone grants no account access. An older account response can displace a newer cookie in the browser, but its superseded bearer is rejected by the server. Signing in again restores access. Independent first requests that share no previously established browser credential cannot be correlated. Anonymous bootstrap, guest setup, recovery writes and actions that can end the browser session share an IndexedDB writer across tabs. A browser without usable IndexedDB can still explicitly revoke its account without receiving a replacement cookie from that write. Each anonymous grant may have one active issuance and can replace an unconfirmed empty capability once after a 15-second delivery grace. The guest cookie is the sole bearer for existing guest demos. Guest setup and password recovery reserve their operation deadlines within an anonymous grant's 30-minute cap. An in-place extension sends no cookie. When a replacement grant is required, the same transaction transfers the still-valid recovery claim or receipt and guest delivery association and revokes the old bearer and its login proofs. For up to 60 seconds, and only through the preceding grant's original expiry, status bootstrap can reissue the same replacement if it receives both the exact previous bearer and its matching browser-binding cookie. Neither cookie alone can restore the association. [Session grants](../backend/src/security.ts) · [Session ordering tests](../backend/tests/auth-session.test.ts) · [Guest lifecycle tests](../backend/tests/setup-guest.test.ts)

Anonymous maintenance also transfers the authority to finish each existing guest upload reservation through its original stream deadline. The upload must still have its original guest bearer, owner and CSRF and pass current policy. The transferred authority applies only to publishing that reservation. Sign-in and sign-out retire it, including anonymous sign-out confirmation. [Upload revalidation](../backend/src/server.ts) · [Guest upload regression cases](../backend/tests/setup-guest.test.ts)

## Authorization and lifecycle rules

- Anonymous browser bootstrap issues a session and separate CSRF value. Password or Steam proof yields a challenge when factors are enrolled, enrollment-only access when policy requires an absent factor, or a full session when the policy permits it. Discoverable passkey login with user verification can establish a full session. A challenge session can complete its indicated second factor or sign out. Enrollment-only sessions can enroll the required factor or sign out. While a member has a pending or full account session, the browser uses only that account’s authority. Sign out to use a still-active guest capability in the same browser.
- A full account can manage its own sessions, passkey labels, factors, password, and provider identities within route and freshness rules. A second-factor recovery code can finish a login challenge. Sensitive mutations require separate qualifying proof. A new factor requires recent primary proof for initial enrollment and existing factor proof for subsequent enrollment. Any async credential or provider operation must recheck live authority before publishing a change.
- `member` and `admin` are server roles. `MFA_REQUIRED_ROLES` defaults to `admin` and can lock the effective setting. The optional `ADMIN_ALLOWED_IPS` restriction adds exact client-address checks on admin pages and APIs. Requests whose addresses cannot be established from a trusted chain are denied admin access when the restriction is enabled. An out-of-range admin retains ordinary member permissions. Last-usable-admin checks cover effective credential and factor policy as well as role. The server retires ineligible grants after a policy change. After a save, the browser reads its current session and never requests a separate browser-wide sign-out on the policy’s behalf.
- Public/guest policy, owner identity, shared state and capability expiry still govern demo reads. Owner mutations use ownership and fresh session or capability checks as applicable. Admin user-management responses may include identifiers, roles, factor metadata, storage totals and session metadata. Full bearer values, verifiers, factor seeds and member-private content are excluded. Password reset code issuance is a separate fresh, audited operation.

Authenticator setup shares one pending key across tabs in the exact authenticated session. Reopening the setup leaves the original deadline in place, which is bounded by the qualifying proof and session lifetimes.

Passkey setup permits one active attempt per authenticated session grant. The browser selects it with a random value saved in tab data before requesting options. A retry with that selector and the exact grant redelivers the last committed phase at its original deadline. The selector alone grants no access. A browser that copies tab data may carry the same selector into the copy. If tab storage is blocked, the open document can still retry.

The creation challenge and possession check share a fixed deadline capped by the qualifying proof and the session’s absolute and idle lifetimes. The server derives each challenge from the grant bearer, a random server nonce and the phase. SQLite keeps the challenge and selector hashes. A cancelled selector blocks delayed replay until the original proof expires. Activation consumes the staged key, revokes the user’s previous sessions and rotates the active grant.

The browser subtracts elapsed monotonic time since each options request from the native timeout hint. It skips expired prompts, asks the browser to abort at the deadline, and discards late credential results. Native UI behavior depends on the browser, operating system and authenticator. If setup stops after the device creates a key and before account activation, the device or password manager may retain it without a corresponding account credential.

The browser retains new account backup codes in memory until it verifies the exact session issued by the factor operation. A temporary verification failure keeps the codes concealed and permits a read retry. A verified replacement session discards the codes.

An administrator’s reset link for another account belongs to the exact session that issued it, including a session created by step-up. If the proof response is lost after rotation, the retired prompt closes and the user confirms the action again. The browser conceals a returned link during interrupted verification. Both self-reset and delegated reset use the remaining server lifetime. It can display the link again within its original lifetime after confirming the same session and administrative access.

Each password reset has an immutable, server-assigned claim ID. With Web Crypto, the browser derives a separate receipt from the reset code before submission. A status read can recognize that issuance after a lost reply or a verified transfer during anonymous renewal. If CSRF changes within the same anonymous grant, the user can retry with the current CSRF. A different grant may resume a transferred claim through its status without resubmitting the code. Completion rechecks the original verifier, account and generation after password hashing. HTTP development browsers without Web Crypto support code submission and completion. If the initial response is lost there, retry in the same grant or request a new reset if the grant has ended.

The recovery screen shows the password form or completed username only after paired session and configuration verification and a matching unexpired status receipt. Foreground checks conceal both until the current receipt is verified again. An entered password can remain in the concealed input for the same live claim and is discarded at expiry or when the claim changes. The browser applies the server’s remaining lifetime from the start of the request using its monotonic clock. Recovery status reads have a 15-second deadline. The browser can retry an interrupted read or reload the page without repeating the password change.

## Email identity and mailbox proof

Only a full account's own status and authorized administrator detail expose its address. A new Steam identity supplies no email evidence. The user enters their address, and linking a provider leaves that address intact. Mail confirmation requires the signed-in owner and possession of the delivered link. Registration, verification and recovery use separate authorizations. A person with a password-reset email can change the password but must still satisfy any enrolled second factor. Operator bootstrap avoids a dependency on mail relay availability.

The web process holds the fixed relay configuration. The parser and speech workers receive no SMTP credentials. Delivery has explicit work and time limits. Verification and email reset links use random, single-use values, with verifiers in SQLite and secrets in URL fragments. Email requests do not reveal whether a reset is eligible. The relay and the recipient’s inbox can read message links. Public registration enforces email uniqueness, so its outcome can disclose address availability. The anonymous password-reset request gives the same response for eligible and ineligible addresses. An unavailable relay can delay onboarding, and an unverified address reservation can require operator assistance to release. See the operator guide for the delivery toggle and manual recovery. ## Administrative audit

For each administrator, the server records the first successful account detail read per target and the first attributable routine denial per action in each minute. The server admits up to 20 sampled reads and 20 sampled denials per administrator each minute, with instance-wide limits of 120 per minute for each. GET and HEAD share an account detail sample. Public and member denials retain their address and account sampling. Sampling affects only the audit record.

Periodic count-based cleanup retains up to 3,000 operator detail reads and 5,000 routine operator denials in independent groups. Completed operator changes and authorized publication events have their own capacity. A publication appends a separate outcome linked to its authorization, and cleanup removes the linked rows together. Worker maintenance also expires audit history after 90 days.
